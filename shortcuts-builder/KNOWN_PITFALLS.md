# KNOWN_PITFALLS

## Purpose

Index of known pitfalls by action identifier. Check this table before generating XML to avoid repeating mistakes. Each entry records: pitfall description, correct form, wrong form, source.

---

## General Pitfalls

### P-GEN-01: Display parameters must use TokenString

**Affected actions**: Notification, Show Result, Alert, Show Alert

**Pitfall**: Display parameters (user-visible text) must use `WFTextTokenString` even when referencing only a single variable. Using `WFTextTokenAttachment` makes the field show empty/default text at runtime.

**Correct**: 
```xml
<key>Text</key>
<dict>
    <key>Value</key>
    <dict>
        <key>string</key>
        <string>￼</string>
        <key>attachmentsByRange</key>
        <dict>
            <key>{0, 1}</key>
            <dict>
                <key>OutputUUID</key><string>UUID-HERE</string>
                <key>OutputName</key><string>Text</string>
                <key>Type</key><string>ActionOutput</string>
            </dict>
        </dict>
    </dict>
    <key>WFSerializationType</key>
    <string>WFTextTokenString</string>
</dict>
```

**Wrong**: Wrapping the variable reference in `WFTextTokenAttachment`.

**Source**: Verified against the 127-shortcut corpus + runtime testing

---

### P-GEN-02: If conditions must explicitly set WFInput

**Affected actions**: `is.workflow.actions.conditional`

**Pitfall**: All condition codes (including numeric codes 0-3) must explicitly set `WFInput` to a Variable wrapper. There is no "implicit input" mode — older docs claiming numeric codes use implicit input were wrong.

**Correct**: 
```xml
<key>WFInput</key>
<dict>
    <key>Type</key><string>Variable</string>
    <key>Variable</key>
    <dict>
        <key>Value</key>
        <dict>
            <key>OutputUUID</key><string>UUID-HERE</string>
            <key>OutputName</key><string>Text</string>
            <key>Type</key><string>ActionOutput</string>
        </dict>
        <key>WFSerializationType</key>
        <string>WFTextTokenAttachment</string>
    </dict>
</dict>
```

**Wrong**: Omitting WFInput or wrapping it in `WFTextTokenString`.

**Source**: Verified against official Apple sample shortcuts

---

### P-GEN-03: Placeholder positions must not be hand-computed

**Pitfall**: The `{position, 1}` in `attachmentsByRange` must point exactly at the position of the `￼` character. Counting character positions by hand is very error-prone, especially with emoji or multi-byte characters.

**Correct**: Compute with `scripts/placeholder-range`.

**Source**: Repeatedly hit in practice

---

### P-GEN-04: Repeated-pattern UUIDs

**Pitfall**: Using UUIDs with repeated patterns such as `11111111-1111-1111-1111-111111111111`. The validator rejects them.

**Correct**: `python3 -c "import uuid; print(str(uuid.uuid4()).upper())"`

---

### P-GEN-05: Comments must not contain WF key names or UUIDs

**Pitfall**: Writing plist technical terms such as `WFInput` or `OutputUUID` in Comment text.

**Correct**: `- Input uses the formatted date from Format Date above`
**Wrong**: `- WFInput references UUID A1B2C3D4...`

**Source**: Validator rule

---

### P-GEN-06: The second Comment must contain fixed text

**Pitfall**: The second Comment action lacks `Shortcuts generated by Shortcuts Playground.`.

**Source**: Validator rule

## Replace Text Pitfalls

### P-REPLACE-01: WFInput referencing ActionOutput must use TokenString

**Affected actions**: `is.workflow.actions.text.replace`

**Pitfall**: When Replace Text's `WFInput` references an ActionOutput, it must use `WFTextTokenString` (with the `￼` placeholder). Do not use a bare `WFTextTokenAttachment`, and do not wrap the ActionOutput with `Type=Variable`.

**Exception**: A Variable wrapper may be used when referencing a Named Variable.

**Source**: CleanText case in practice (2026-05-28)

---

### P-REPLACE-02: WFReplaceTextReplace pure constants must not use TokenString

**Pitfall**: Wrapping a pure-constant replacement value in `WFTextTokenString`. The validator's `iter_empty_strings` calls `.strip()` on the `string` key inside `WFTextTokenString`, so a whitespace-only replacement value is judged empty.

**Correct**: Use a plain `<string>` for pure-constant replacement values.

**Source**: CleanText case in practice (2026-05-28)

---

### P-REPLACE-03: Replacing on rich-text input is ineffective

**Pitfall**: Content obtained from the clipboard or share input may be a rich-text object; running a Replace Text regex directly on rich text may be ineffective.

**Correct**: Insert a Text action (`gettext`) before Replace Text, referencing the input variable via TokenString, to force coercion to a plain-text string.

**Wrong**: Using `getmarkdownfromrichtext` (it leaves Markdown markers behind).

**Source**: CleanText case in practice (2026-05-28)

## Find Notes Pitfalls

### P-NOTES-01: Searching by title must use Operator 99

**Affected actions**: `is.workflow.actions.filter.notes`

**Pitfall**: When searching notes by title, using `Operator = 4` (equals) instead of `Operator = 99` (contains). Operator 4 fails to match the expected note in some cases.

**Correct**: `Property = Name`, `Operator = 99`

**Source**: XML Snippet Patterns + verified in practice

---

### P-NOTES-02: Append to Note's WFNote is not a title string

**Affected actions**: `is.workflow.actions.appendnote`

**Pitfall**: Setting `WFNote` to a note-title string. `WFNote` must be a Note object reference (from Find Notes output), not a title string.

**Source**: XML Snippet Patterns

---

## Weather Pitfalls

### P-WEATHER-01: Weather Detail must not go through a Named Variable

**Affected actions**: `is.workflow.actions.properties.weather.conditions`

**Pitfall**: Storing the weather output in a Named Variable first and then passing it to Get Detail of Weather Conditions. This degrades the property name to the generic "Detail".

**Correct**: Reference the ActionOutput of Get Current Weather / Get Weather Forecast directly.

**Source**: BEST_PRACTICES

---

### P-WEATHER-02: Sunrise/Sunset are lists

**Pitfall**: `Sunrise Time` and `Sunset Time` obtained from the Daily forecast are lists and cannot be passed directly to Format Date.

**Correct**: Add Get Item from List first (First Item for Sunrise, Last Item for Sunset).

**Source**: BEST_PRACTICES

---

### P-WEATHER-03: WFContentItemPropertyName must not be left as "Detail"

**Pitfall**: `WFContentItemPropertyName` left as the placeholder value `Detail` instead of the actual property name.

**Correct values**: `Temperature`, `Humidity`, `Condition`, `Sunrise Time`, etc. (see ACTION_PARAM_INDEX #12; the full list is in BEST_PRACTICES).

## Date Pitfalls

### P-DATE-01: Get Time Between Dates must not use the CurrentDate magic token

**Affected actions**: `is.workflow.actions.gettimebetweendates`

**Pitfall**: Using the `CurrentDate` magic token directly in `WFTimeUntilFromDate`. After import it shows as empty/default date.

**Correct**: Insert a Date action set to Current Date first, then reference that Date action's output.

**Source**: BEST_PRACTICES

---

### P-DATE-02: Date parameters must use TokenString

**Affected actions**: `is.workflow.actions.gettimebetweendates`

**Pitfall**: Using a bare `WFTextTokenAttachment` for date parameters. It passes structural validation, but after import shows "First Date" / "Second Date" placeholders.

**Correct**: Use `WFTextTokenString` for both `WFInput` and the date operands.

---

## Health Pitfalls

### P-HEALTH-01: Do not set WFHealthQuantityType

**Affected actions**: `is.workflow.actions.filter.health.quantity`

**Pitfall**: Setting the top-level `WFHealthQuantityType`. Current iOS Shortcuts ignores this obsolete key, so it renders as generic Health Samples.

**Correct**: Put the sample type in the Type predicate row of `WFContentItemFilter` (Operator 4, Bounded true, Removable false).

---

### P-HEALTH-02: Use the Find Health Samples picker label

**Pitfall**: Using SDK names (such as `Sleep Analysis`, `Active Energy Burned`) instead of the picker label.

**Correct label**: `Sleep` (not Sleep Analysis), `Exercise Minutes` (not Exercise Time), `Active Calories` (not Active Energy).

---

### P-HEALTH-03: Sleep Duration is in seconds

**Pitfall**: Dividing Sleep Duration by 60 and treating it as "hours". After Math coercion it is actually in seconds.

**Correct**: Divide by 3600 for hours, by 60 for minutes.

---

## Calendar Pitfalls

### P-CAL-01: Find Calendar Events date filter must not use Operator 3

**Affected actions**: `is.workflow.actions.filter.calendarevents`

**Pitfall**: Using `Operator: 3` to filter future events. After import it shows as a red invalid condition.

**Correct**: Use `Operator: 1002` (is today) + `Operator: 2` (is after Current Date).

## API / HTTP Pitfalls

### P-API-01: JSON booleans are coerced to numbers

**Pitfall**: `true`/`false` in a JSON response are converted to `1`/`0` in Shortcuts. A string check with `Contains "true"` will fail.

**Correct**: Use a numeric condition (`Is Greater Than 0` or `Equals 1`).

---

### P-API-02: JSON null is coerced to empty

**Pitfall**: Comparing JSON null using the string `"null"`.

**Correct**: Use If Has Any Value (code 100) / Does Not Have Any Value (code 101).

---

### P-API-03: WFJSONValues renders nested objects incorrectly

**Pitfall**: Using `WFJSONValues` for complex nested JSON leads to Number 0, empty rows, or data loss.

**Correct**: Use a JSON Text action + `WFRequestVariable` + Body Type = File + Content-Type: application/json instead.

---

### P-API-04: Orphan JSON Text action

**Pitfall**: Creating a JSON Text action that is not referenced by any `WFRequestVariable`.

**Correct**: Every JSON Text must be the `WFRequestVariable` of some request, or be deleted.

## Location Pitfalls

### P-LOC-01: Location parameters must not use TokenString

**Affected actions**: `WFLocation`, `WFWeatherCustomLocation`, `WFWeatherLocation`

**Pitfall**: Using `WFTextTokenString` for location parameters.

**Correct**: Use `WFTextTokenAttachment` to reference the output of Get Current Location / Location directly.
